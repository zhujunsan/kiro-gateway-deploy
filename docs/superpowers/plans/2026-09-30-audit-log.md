# 请求审计记录（Audit Log）实现计划

> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax for tracking. 每个 Task 完成后更新下方「执行进度」表。

**Goal:** 满足公司审计要求：把经过本机网关的每一次对话请求与响应完整记录下来，按用户 / 日期分区压缩后定期上传到阿里云 OSS，永久保存，供日后审计分析。是否开启由云端下发，OSS 上传凭证由云端按文件签发。

**Architecture:**

```
客户端（Cursor / Claude Code / Codex …）
   │  POST /v1/chat/completions | /v1/messages | /v1/responses
   ▼
网关子进程 —— 只做「抓取 + 原样落盘」，不联网、不压缩、不去重
   └── AuditCapture 中间件（新增 audit_capture.py）
         │ 旁路复制请求体 + 原始响应字节，零缓冲转发
         │ 读 audit/control.json 决定是否记录（tray 写，子进程只读）
         ▼ 写线程：每请求一行原始 JSON → audit/spool/<段>.jsonl，每 60 秒改名为 .ready
                                  │  （文件交接，无 IPC）
tray 主进程（挂在 Supervisor 上，托盘 / CLI 两种模式共用）
   ├── ClientConfigPoller：POST Worker /client-config → 写 audit/control.json
   ├── IdentityRefresher：GET 本机 /usage?raw=true → kiro_user_id / email
   ├── AuditPipeline：吃 .ready → 剥离图片 → 按消息切块 → sha256 去重 → 当前批次
   │        每 10 分钟 / UTC 跨日：封段 → zstd 压缩 → outbox/
   └── AuditUploader：POST Worker /audit/upload-url 拿预签名 PUT → 直传 OSS

Cloudflare Worker（复用 kiro-provision）
   ├── POST /client-config      激活码鉴权；读 D1 client_config，边缘缓存
   └── POST /audit/upload-url   激活码鉴权；校验对象路径在 <username>/ 下；
                                用 RAM 子账号 AK 生成 OSS V4 预签名 PUT URL
阿里云 OSS
   └── audit/v1/YY-MM-DD/<IdC userId>/<batch>.{req,blob}.jsonl.zst
```

**Tech Stack:** Python 3.11（网关子进程只加抓取中间件，其余在 tray 主进程，不改 vendor）、`zstandard`（新增唯一运行时依赖，只在 tray 主进程使用）、Cloudflare Worker + D1（WebCrypto 做 OSS V4 签名，零依赖）、阿里云 OSS、DuckDB（分析侧，非运行时依赖）。

## 一、已定决策

| 议题 | 决策 |
|---|---|
| 实现位置 | 只改本仓 tray app，**不改上游 / vendor**。网关子进程只加一个抓取中间件（复用 `gateway.py` 里包 `main.app` 的注入点）；处理、去重、压缩、拉配置、上传全部在 tray 主进程 |
| 记录什么 | 客户端发给网关的原文 + 网关返回给客户端的原始字节。**不记**网关转换后发给 Kiro 的 payload（由网关代码版本决定、可复现） |
| 记录范围 | `POST /v1/chat/completions`、`/v1/messages`、`/v1/responses`（与遥测 `COLLECT_PATHS` 一致） |
| 开关 | 云端下发，只有 `off` / `best_effort` 两档。`best_effort`：审计任何环节失败都**不影响**请求 |
| 身份 | 信任客户端上报的 `username`（现有机器指纹）；另附 `kiro_user_id`（IdC 用户 ID）与 `email`（非空时） |
| 上传凭证 | 每个文件现场向 Worker 要一次预签名 PUT URL，客户端不持有任何 AK |
| 大体积内容 | 图片 / PDF 等 base64 内容本期丢弃，只留占位（类型、字节数、sha256） |
| 保留期 | OSS 上**永久保留**，不配删除型生命周期规则 |
| 本地积压上限 | 默认 **1 GB**，按**压缩后**的 outbox 文件 + 当前未封段文件计；超限丢最旧批次 |
| 告知 | 已在下载时告知，客户端代码里不做告知 UI |
| 请求头脱敏 | `authorization`、`x-api-key`、`proxy-authorization`、`cookie`、`cf-access-client-secret` 替换为 `"<redacted>"` |

### 为什么不做逐轮 delta，而做消息级去重

逐轮 delta 依赖「本轮 = 上一轮 + 新消息」，但客户端会压缩历史、截断、在系统提示词里嵌时间戳、挪 `cache_control` 标记，还要识别会话归属、处理并发会话；链条中间丢一批，后续全部无法还原。消息级内容寻址去重不依赖顺序和会话识别，任何一段内容只存一次，改写只影响被改的那一条。

### 身份字段来源（已在本机核实）

- `kiro-auth-token.json` 里 `accessToken` 是不透明令牌，**没有**邮箱；Kiro IDE 本地存储也没有。
- 网关现有 `GET /usage?raw=true`（fork 内已有，调 `getUsageLimits`）返回 `userInfo`：
  - `userId`：格式 `d-xxxxxxxxxx.<uuid>` =「IdC 身份库 ID.用户 ID」，企业账号稳定可用。
  - `email`：企业 IdC 账号下为 `null`，其他登录方式可能有值（未验证）。
- 映射到员工：IdC 管理员执行一次 `aws identitystore list-users --identity-store-id d-xxxxxxxxxx` 导出 `UserId / UserName / Emails` 即可，不对接 SSO。

## 二、数据结构

### OSS 对象路径

```
audit/v1/<YY-MM-DD>/<IdC userId>/<批次开始 UTC 时间>-<8 位随机>.req.jsonl.zst
audit/v1/<YY-MM-DD>/<IdC userId>/<批次开始 UTC 时间>-<8 位随机>.blob.jsonl.zst
```

- Hive 风格分区，DuckDB（`hive_partitioning=true`）/ MaxCompute 外表可直接按 `dt`、`user` 裁剪。
- 分区日期统一用 **UTC**；记录内时间戳为 Unix 秒（浮点），分析时再按需转北京时间。
- 一个批次永不跨 UTC 日（跨日强制封段）。
- 一个批次两个文件必须同时存在才算完整；`blob` 可能为空文件（本批无新内容）。

### 请求记录（`*.req.jsonl.zst`，每行一个请求）

```json
{
  "v": 1,
  "id": "uuid4",
  "ts_start": 1759200000.123,
  "ts_end": 1759200012.456,
  "username": "8bd53a8e0092",
  "kiro_user_id": "d-xxxxxxxxxx.uuid",
  "email": null,
  "app_version": "0.4.49",
  "upstream_sha": "d1d5891",
  "os": "darwin",
  "via": "tunnel",
  "remote_ip": "1.2.3.4",
  "method": "POST",
  "path": "/v1/messages",
  "req_headers": {"user-agent": "claude-cli/…", "x-api-key": "<redacted>"},
  "req_bytes": 812345,
  "req": {
    "params": {"model": "claude-sonnet-4.5", "stream": true, "max_tokens": 32000},
    "blobs": {"system": "sha256…", "tools": ["sha256…"], "messages": ["sha256…", "sha256…"]},
    "raw": null
  },
  "dropped": [{"path": "messages[3].content[1]", "kind": "image", "media_type": "image/png", "bytes": 482113, "sha256": "…"}],
  "status": 200,
  "resp_headers": {"content-type": "text/event-stream"},
  "resp_bytes": 20480,
  "resp": {"raw": "event: message_start\ndata: …", "truncated": false},
  "completed": true,
  "error": null
}
```

字段规则：

- `via`：请求头带 `cf-ray` 视为 `tunnel`，否则 `local`。`remote_ip` 取 `cf-connecting-ip`，本地请求为 `null`。
- `req.params`：请求体顶层中**未被切成 blob** 的字段原样保留。
- `req.raw`：请求体不是合法 JSON 对象时，存 UTF-8 解码后的原文（`errors="replace"`），此时 `params` / `blobs` 为空。
- `resp.raw`：原始响应字节（SSE 原样，不做拼接），上限 20 MB，超出截断并置 `truncated: true`。
- `completed`：响应是否正常结束（客户端中途断开 / 网关异常为 `false`）；`error` 为异常类名。
- 每条记录自带完整身份字段（不依赖文件名），便于跨分区合并分析。

### blob 记录（`*.blob.jsonl.zst`，每行一块内容）

```json
{"h": "sha256…", "body": {"role": "user", "content": "…"}}
```

### 切块规则（格式无关，不按 OpenAI / Anthropic 分支写死）

1. 先做**媒体剥离**：递归遍历请求体，命中下列形态的 base64 内容替换为占位对象 `{"_dropped": "<kind>", "bytes": N, "sha256": "…"}`，并追加一条到 `dropped`：
   - `{"type": "image" | "document", "source": {"type": "base64", "data": …}}`（Anthropic）
   - `{"type": "image_url", "image_url": {"url": "data:…"}}`（OpenAI Chat）
   - `{"type": "input_image", "image_url": "data:…"}`、`{"type": "input_file", "file_data": …}`（OpenAI Responses）
   - 兜底：任意 `data:<mime>;base64,` 开头且长度 > 4 KB 的字符串
2. 请求体顶层每个**数组**字段（`messages`、`input`、`tools`…）按元素切块。
3. 其余顶层字段中，规范化 JSON 长度 > 2 KB 的（`system`、`instructions`…）整体作为一块。
4. 块哈希 = `sha256(json.dumps(块, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode())`。
5. 去重范围 = **同一台机器、同一 UTC 日**：当天已写过的哈希不再写 blob。进程重启后集合从当天已封段 + 当前段的 blob 文件重建（只读哈希列）；重建失败则退化为重复写，不影响正确性。
6. 写入顺序：同一请求先写其新 blob 行，再写 req 行，保证任意时刻 req 引用的 blob 已落盘。

还原：req 记录里 `blobs` 的哈希按原字段名 / 原顺序替换为 blob 的 `body`，再合并 `params`，即得去除媒体后的原请求体。

## 三、本地落盘与积压

目录：`<data_dir>/audit/`

```
audit/
  control.json                     tray 写、子进程读：{"mode": "off"|"best_effort", "max_spool_bytes": N}
  spool/<段开始时间>-<pid>.jsonl    子进程正在写的原始段（每请求一行，未去重、未剥离图片）
  spool/<段开始时间>-<pid>.ready    子进程已关闭、等 tray 处理的原始段
  current/<batch>.req.jsonl        tray 当前批次（去重后明文追加）
  current/<batch>.blob.jsonl
  outbox/<YY-MM-DD>/<IdC userId>/<batch>.req.jsonl.zst   已封段待上传（路径 = OSS 对象 key 去掉 audit/v1/ 前缀）
  outbox/<YY-MM-DD>/<IdC userId>/<batch>.blob.jsonl.zst
  state.json                       tray 私有：云端配置缓存、身份缓存、丢弃计数
```

### 子进程 → tray 的文件交接协议

- 子进程每 60 秒关闭当前原始段并改名为 `.ready`，再开新段。只有关闭后的文件才会被改名（Windows 下不能改名打开中的文件）。
- 子进程启动时先把 `spool/` 下遗留的 `.jsonl`（上一个子进程崩溃留下的）全部改名为 `.ready`。`proc_guard` 保证同一时刻只有一个网关子进程，所以不需要 pid 存活判断。
- 原始段最后一行若不完整（崩溃截断），tray 处理时丢弃该行。
- tray 把一个 `.ready` 的所有记录写进当前批次并 fsync 后才删除它；中途崩溃会导致重复处理，靠记录 `id` 去重（分析侧 / 还原脚本处理）。
- 原始行格式：第二节请求记录里除 `kiro_user_id`、`email`、`req`、`dropped` 之外的字段，另加 `req_body`（请求体 UTF-8 文本）。身份字段和切块由 tray 处理时补上。

### tray 侧批次与封段

- **封段时机**：距批次开始满 `rotate_seconds`（默认 600）、UTC 跨日、或 tray 启动时发现遗留的 `current/` 批次。
- **封段**：流式 zstd 压缩（level 10，`long_distance_matching` 开启，窗口 27）→ 写临时文件 → `os.replace` 进 outbox → 删除明文批次。
- **tray 退出**：`Supervisor.stop()` 时把已有 `.ready` 处理完并 flush 当前批次，不压缩；封段留到下次启动。

### 积压与内存上限

- **积压上限**：`spool + current + outbox` 总大小 > `max_spool_mb`（默认 1024）时，tray 从 outbox 最旧批次开始成对删除，`state.json` 里 `dropped_batches` 累加并 `logger.warning`。
- **子进程兜底**：子进程每次换段时检查 `spool/` 总大小，超过 `control.json` 里的 `max_spool_bytes`（说明 tray 没在消费）就暂停记录并计数，直到空间回落。防止 tray 卡死时原始段把磁盘写满。
- **子进程写入队列**：按字节计上限 256 MB；满了直接丢弃该请求记录（`best_effort` 语义，不阻塞请求）。
- **文件权限**：POSIX 下 `audit/` 目录 0700、文件 0600。

## 四、云端接口

### `POST /client-config`

- 请求：`{"shared_secret", "username"}`，`User-Agent: KiroGatewayTray/<version> (<platform>)`（与 `/announcements` 相同鉴权方式）。
- 响应：`{"ok": true, "audit": {"mode": "off" | "best_effort", "rotate_seconds": 600}}`
- 数据源：D1 表 `client_config(key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at INTEGER)`，`audit` 行的 `value` 形如 `{"mode": "best_effort", "usernames": []}`。`usernames` 非空时只对名单内用户返回 `best_effort`，其余返回 `off`（用于灰度）。
- 缓存：复用公告的边缘缓存 + 缓存世代机制，TTL 5 分钟。
- 这是**通用客户端配置接口**，审计只是第一个字段，以后的远程开关都加在这里。

### `POST /audit/upload-url`

- 请求：`{"shared_secret", "username", "keys": ["audit/v1/<YY-MM-DD>/<IdC userId>/<batch>.req.jsonl.zst", "…blob.jsonl.zst"]}`
- 校验：激活码；`username` 符合 `USERNAME_RE`；每个 key 匹配
  `^audit/v1/\d{2}-\d{2}-\d{2}/(<username>|<IdC userId>)/[0-9]{8}T[0-9]{6}Z-[0-9a-f]{8}\.(req|blob)\.jsonl\.zst$`；目录优先用 userId，单次最多 10 个 key。
- 响应：`{"ok": true, "uploads": [{"key", "url", "headers": {"x-oss-forbid-overwrite": "true"}}]}`，URL 有效期 15 分钟。
- 签名：OSS V4（`OSS4-HMAC-SHA256`）预签名 PUT，`x-oss-forbid-overwrite` 纳入签名，客户端不带就会被 OSS 拒绝。
- Worker Secrets / Vars：`OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`（secret）；`OSS_BUCKET`、`OSS_REGION`（如 `cn-hangzhou`）、`OSS_ENDPOINT`（如 `oss-cn-hangzhou.aliyuncs.com`）（vars）。未配置时返回 `503 {"error": "audit storage not configured"}`。

### 客户端上传语义

- `200` → 删除本地文件。
- `409 FileAlreadyExists` → 视为已上传成功（上次成功但响应丢失），删除本地文件。
- `403`（URL 过期等）→ 下一轮重新要 URL。
- 其他失败 → 指数退避（30 s 起，上限 1 h），不删文件。
- 顺序：先 blob 后 req，同批次两者都成功后才算完成；批次间按时间从旧到新（FIFO）。
- 网络：OSS 直传使用 `httpclient.resolve_proxy()` 的同一套代理规则（与 Worker 调用一致）；若实测跨境代理导致上传慢，再在 `/client-config` 里加开关。

## 五、开关优先级与模块归属

模式判定由 tray 完成（高 → 低），结果写进 `control.json`：

1. 本地 `config.toml` `[audit] mode_override`（`""` 表示不覆盖；`"off"` / `"best_effort"`）—— 仅用于阶段一本机测量和排障。
2. 最近一次成功拉到的云端配置（内存）。
3. `state.json` 里缓存的云端配置（离线重启时沿用）。
4. 默认 `off`。

子进程只认 `control.json`：文件不存在或解析失败一律视为 `off`；按 mtime 缓存，最多每 5 秒检查一次，改开关不需要重启网关。模式切换只影响**之后开始**的请求；切到 `off` 后，已积压的文件照常处理和上传。

### 模块归属

| 进程 | 模块 | 职责 |
|---|---|---|
| 网关子进程 | `audit_capture.py`（新增） | 中间件抓取、写原始段、换段、读 `control.json`、磁盘兜底 |
| 网关子进程 | `gateway.py` | 在 `telemetry.wrap_app` 之后加一行 `app = audit_capture.wrap_app(app)` |
| tray 主进程 | `audit_payload.py`（新增） | 媒体剥离、切块、哈希、还原（纯函数） |
| tray 主进程 | `audit_pipeline.py`（新增） | 消费 `.ready`、去重、批次、封段、积压上限 |
| tray 主进程 | `audit_uploader.py`（新增） | 拉 `/client-config`、写 `control.json`、刷新身份、上传 |
| tray 主进程 | `supervisor.py` | `start()` / `stop()` 里启停上面这些后台线程；托盘和 CLI 两种模式都走 `Supervisor`，不用分别接线 |
| tray 主进程 | `appconfig.py` | 新增 `[audit]` 段（`mode_override`、`max_spool_mb`、`rotate_seconds`） |

子进程侧不联网、不引入 `zstandard`、不需要 Worker 地址和激活码，也不需要新增环境变量（数据目录用 `paths.data_dir()`，`username` 和 `app_version` 沿用已注入的 `TELEMETRY_USERNAME`、`APP_VERSION`）。

身份：tray 调本机 `GET /usage?raw=true`（带 `PROXY_API_KEY`，复用 `usage.py` 的本地连接池），取 `userInfo.userId` / `email`，每小时刷新一次并缓存到 `state.json`，处理 `.ready` 时补进记录；取不到时记为 `null`，不阻塞处理。

| 项 | 估算 | 合成样本（2026-09-30） | 线上实测 |
|---|---|---|---|
| 消息级去重后剩余比例 | 5–10% | 1.8% | ⬜ |
| zstd 再压缩比 | 5× | blob 约 34×；加上仍要存哈希的 req 段，相对原文约 870× | ⬜ |
| 最重用户每天上传量 | 30–50 MB | 若比例成立，约数 MB/天（不能当承诺） | ⬜ |
| 1 GB 积压可撑离线时长（最重用户） | 3–4 周 | 合成比例下远超一个月 | ⬜ |
| OSS 年新增存储（全体） | 数十 GB | 合成比例下个位数 GB | ⬜ |

合成样本不是线上流量：120 次请求，每次把此前全部轮次原样重发（user 约 1 KB、assistant 约 2 KB），共用一个 `seen` 集合，压缩参数与 `audit_pipeline._compressor` 相同。原文 18.6 MB，去重后 blob 328 KB，zstd 后 blob+req 共 21 KB。这是去重最有利的形态（历史整段重复）。工具输出每次都变的会话会差一截，所以估算列先不动。本机打开 `mode_override = "best_effort"` 用一两天后，跑 `python app/scripts/audit_stats.py` 再填「线上实测」列。

- [ ] `strip_media(body: dict) -> tuple[dict, list[dict]]`：按第二节规则剥离媒体，返回新对象（不修改入参）与 `dropped` 列表。

## 八、已知边界

- 客户端记录本质上是「正常使用下留痕」，用户改本地配置、屏蔽 Worker 或直接跑上游网关都可以绕过；本期接受。
- `username` 由客户端上报、不做校验，持有激活码的人理论上可以以任意 username 申请上传 URL；本期接受。
- 积压超限删除旧批次时，同日后续批次若引用了被删批次里的 blob，这部分请求无法完整还原；还原脚本会报出缺失哈希。
- 记录的是客户端视角的原文，不含网关转换后发给 Kiro 的 payload。

## 附录：还原与 DuckDB

先把某个 `user=` 分区（或 `audit_rebuild.py` 的输出）放到本地。还原脚本会把跨批次的 blob 拼回去，缺哈希时退出码为 1，并在 stderr 打出 `missing blob <sha256>`。

```bash
python app/scripts/audit_rebuild.py ./audit/outbox --user alice \
  --kiro-user-id 'd-xxxxxxxxxx.uuid' --start 1759190400 --end 1759276800 \
  > rebuilt.jsonl
```

下面的查询对着还原后的 JSONL。`body` 是去掉大媒体之后的客户端请求。

```sql
CREATE TABLE rebuilt AS SELECT * FROM read_json_auto('rebuilt.jsonl');

-- 按人按天请求数
SELECT username,
       CAST(to_timestamp(ts_start) AS DATE) AS day,
       count(*) AS requests
FROM rebuilt
GROUP BY 1, 2
ORDER BY 2, 1;

-- 按模型
SELECT json_extract_string(body, '$.model') AS model, count(*) AS requests
FROM rebuilt
GROUP BY 1
ORDER BY 2 DESC;

-- 关键词（搜的是已还原正文，不是压缩文件）
SELECT id, username, ts_start
FROM rebuilt
WHERE body::VARCHAR ILIKE '%退款%';

-- 用一次性导出的 Identity Center 用户表把 kiro_user_id 对到员工
SELECT r.id, r.username, r.kiro_user_id, e.email
FROM rebuilt r
LEFT JOIN read_csv_auto('identitystore_users.csv') e
  ON r.kiro_user_id = e.user_id;
```

直接扫 OSS 上的 `.jsonl.zst` 时，DuckDB 读的是切块后的行，正文还在 blob 文件里。要看完整请求，先跑还原脚本。分区目录可以用 `hive_partitioning`：

```sql
SELECT user, count(*) AS rows
FROM read_json_auto('audit/v1/*/*/*.req.jsonl.zst')
GROUP BY 1;
```
